## 2. Fatia 1 — modo Manual

**Contrato.** `mode: "auto" | "manual"` (default `"auto"`) nas etapas `bot` e
`script`. `condition` não tem modo: nunca abre turno.

**Estado.** Novo status `waiting_manual` e `hold: { step, since }` no
`run.json`. `waiting_manual` é run ativa: retenção, `DELETE` de Workflow/run e
cancelamento a tratam como `waiting_approval`. Reinício do app preserva a run
parada; ela não retoma sozinha.

**Motor.** Em `advance`, antes de copiar entradas ou abrir thread, se a etapa é
manual e ainda não foi liberada, a run vira `waiting_manual` com
`hold.step = currentStep`. `engine.resume(runId)` valida o status, libera a
etapa e segue o mesmo caminho de início (sem re-parar). A liberação é memória
do processo: depois de reiniciar, a run continua parada até a pessoa clicar.

**Rotas.** `POST /api/workflows/runs/:id/continue` (pessoa) responde 409 fora
de `waiting_manual` e 404 para run inexistente. A run da rotina espelha
`waiting` (já usado na aprovação); cancelamento e timeout continuam valendo.

**UI F2.** Bloco "Aguardando você continuar" no detalhe da run, com etapa,
tempo parado e botão **Continuar**. Ícone circular âmbar com pausa. A lista de
situações ganha o novo estado. A timeline mostra a etapa como
**Aguardando início**, não `running`.

**Studio.** O balão **Execução** ganha "Modo de execução" (Automático/Manual)
para Agente e Script. O painel da etapa na F2 mostra "Manual".

**Decisões aprovadas (09/11/2026).**

1. **Quem continua:** qualquer membro do departamento, como no cartão da
   aprovação (P16).
2. **Rotina:** pode apontar para Workflow com etapa manual, **exceto** quando a
   **primeira etapa** é manual. O bloqueio acontece no editor de rotina e na
   rota que cria/edita a rotina (defesa em profundidade). As demais etapas
   manuais podem ficar onde estiverem; a rotina para e espera a pessoa.
3. **Timeout:** a espera manual **não consome** o `timeoutMs` da etapa. O
   relógio começa ao clicar em Continuar, como na pausa de aprovação.
4. **Notificação:** não entrou na fatia 1; a rodada seguinte a implementou
   somente in-app, como registra a §9.1.

**Testes.** Contrato (default, validação), estado (hold/resume), motor (para,
não abre thread, retoma, reinício preserva), rotas (200/404/409), retenção
(não apaga), rotina (bloqueio quando a primeira etapa é manual) e Studio
(grava `mode`).

## 4. Fatia 3 — Python e TypeScript

**Extensão decide o runtime.** `isWorkflowScriptName` aceita `.mjs`, `.js`,
`.ts` e `.py`. Nada de campo novo: o nome do arquivo já é o contrato.

| Extensão | Comando |
|---|---|
| `.mjs` / `.js` | `process.execPath <arquivo>` (Electron vira Node com `ELECTRON_RUN_AS_NODE=1`) |
| `.ts` | `process.execPath --experimental-strip-types <arquivo>` |
| `.py` | `WORKFLOW_PYTHON ?? (win32 ? "python" : "python3") <arquivo>` |

**Ambiente.** O mesmo `WORKFLOW_STEP_INPUT` / `WORKFLOW_STEP_OUTPUT` /
`WORKFLOW_RUN_ID` / `WORKFLOW_STEP_ID`, `cwd` da etapa e timeout. Python sem
`python3` falha com mensagem clara (`could not find python3 on PATH`), não com
stack genérica.

**Studio.** O seletor **Linguagem** deixa de ser desabilitado: JavaScript,
TypeScript e Python. Trocar a linguagem renomeia `run` mantendo o nome base e
move o conteúdo do editor para o novo arquivo (não perde código).

**F2.** `SCRIPT` mostra o runtime derivado da extensão.

**Testes.** Contrato aceita/rejeita extensões; executor roda `.ts` e `.py`
reais; Studio troca a extensão e preserva o código.

## 5. Fatia 4 — condição E/OU

**Decisão.** A condição deixa de ser uma comparação só e passa a ser um grupo
de linhas fechadas com `match: "all" | "any"`. Expressão livre fica pendente
(seção 9).

**Contrato.**

```ts
condition = {
  kind: "condition";
  from: string;
  match: "all" | "any";            // default "all"
  conditions: Array<{              // 1..20
    field: string;                 // caminho pontuado no result.json
    op: ConditionOp;               // lista fechada de hoje
    value?: unknown;               // exigido exceto em exists
  }>;
  whenTrue?: string;
  whenFalse?: string;
  onFailure?: string;
};
```

- `match: "all"` = todas verdadeiras; `"any"` = pelo menos uma.
- **NÃO** não vira campo: negar é trocar as rotas True/False (o Studio já
  permite reconectar).
- Legado (`field`, `op`, `value` soltos) é normalizado na leitura para
  `conditions: [ ... ]` com `match: "all"`, como já acontece com `next`.
- Limites: 20 linhas, 4 KB por valor, e o JSON do grupo pequeno. A mesma
  validação de caminho/valor da comparação atual.

**Motor.** `condition.ts` avalia cada linha com o comparador que já existe e
combina com `all`/`any`. Erro de tipo ou caminho ausente falha a etapa com a
linha e o campo no texto; a etapa `condition` continua usando `onFailure` (ou
para a run, se não houver).

**UI.** O balão **Condição** vira:

- seletor **Todas / Qualquer**;
- linhas com Campo, Operador, Valor e remover;
- **Adicionar condição**;
- o painel da etapa na F2 mostra o grupo e as duas rotas.

**Testes.** Schema (legado, vazio, máximo, valor por operador), avaliador
(`all`, `any`, erro em uma linha), motor (rotas e falha), Studio (adicionar,
remover, validar) e o painel da etapa.

## 5A. Skills por etapa de agente (fatia adicional)

> **Status: concluída (09/11/2026, commit `55945294b`).** A etapa `bot` passa a
> declarar exatamente as skills que carrega; `script` e `condition` não têm o
> campo.

**Contrato.** `skills?: { bot?: string[]; bundled?: string[]; imported?: string[] }`
na etapa `bot`. Os grupos são independentes, vazio/ausente significa desligado e
não há booleano separado. Limites: 200 nomes do bot, 100 ids bundled e 200 nomes
importados, 64 caracteres por nome, sem repetição. A normalização equipara
`ausente` e `{}`/grupos vazios, então abrir e salvar sem mudar não cria versão.

**Origens.** `bot`: skills próprias + biblioteca atribuída ao bot. `bundled`:
`manifest.id` das skills empacotadas do app. `imported`: nomes descobertos nas
outras ferramentas deste computador. O snapshot de nomes é o padrão; o modo
“all skills” com curinga fica para depois (§9.6).

**Save.** A rota valida cada etapa bot contra as opções daquele bot e recusa com
400 (`step "X": skill "x" is not available for this Workflow step`). A rota
`GET /api/workflows/skill-options?botId=...` devolve os três grupos com nome,
descrição e disponibilidade.

**Motor.** `WorkflowTurnOptions` leva a seleção. Antes de abrir o turno, o motor
confere se todas as skills declaradas ainda existem e falha a etapa com
`skill "x" is not available for this Workflow step`. Bundled declarada carrega
sem depender das palavras-chave de gatilho, respeitando as capabilities
exigidas. Sem seleção, o turno não recebe índice, import nem instrução de skill.
A pasta de skills do bot continua visível na tarefa: a restrição é de
contexto/comportamento, não um sandbox de arquivos.

**Studio.** O card do Agente ganha a ramificação **Skills**, com prévia
“Nenhuma skill”/“1 skill”/“N skills”. O balão tem os três grupos, toggle,
**Selecionar todas as disponíveis**, checkboxes, estado indisponível e aviso de
que as importadas são desta máquina. Ligar um grupo grava todas as opções
disponíveis; desligar limpa. `createStep` nasce sem skills. As opções são
carregadas ao abrir o balão/trocar o bot, com cache por bot.

**F2.** O painel da etapa mostra os grupos e nomes da seleção, ou
**Nenhuma skill**.

**Testes.** Schema (ausente/vazio, grupos, limites, unicidade, script/condition
sem o campo), motor (sem seleção, só bot, bundled sem gatilho, imported e skill
ausente), rotas (aceita/recusa e versão inalterada), Studio (default, toggle,
marcar todas, validação e round-trip) e os componentes do balão/card.

## 9. Pendências registradas

### 9.1 Notificação de run parada

**Decisão desta rodada (09/11/2026): notificação somente in-app, sem SO.** Uma
run que entra em `waiting_manual` gera **uma** notificação no feed e no sino da
interface, na transição e nunca no boot, em reconexão ou em polling. O público
é admin, como as rotas de Workflow. O clique abre a tela de Workflows na aba
Runs com a run e o Workflow dela selecionados. Nada de notificação do sistema
operacional, som, e-mail ou push nesta rodada; `waiting_approval`, conclusão,
falha e cancelamento continuam sem notificação.

**Pendência futura:** decidir se a espera manual também deve notificar fora do
app e por qual canal (SO, e-mail, push etc.), preservando a regra de uma única
notificação por `runId + step` e sem avisar no boot.

### 9.2 Replay a partir de uma etapa (F3.2.1)

Não confundir com o modo Manual: Manual para a run **antes** da etapa e continua
a mesma run. Replay pega uma run **já terminada** e cria uma execução nova
começando em uma etapa escolhida.

Situação hoje: não existe. "Rodar de novo" sempre cria uma run do zero, presa à
mesma versão; a rota de run só aceita `{ version }`. O material no disco
(`step-N/input`, `step-N/output`, `run.json` com snapshot) é o que já ajuda.

Decisões de produto em aberto:

- run nova ou a mesma? (recomendado: run nova, histórico imutável);
- reaproveitar os `output/` das etapas anteriores ou exigir `input/` novo?
- como lidar com efeitos colaterais já feitos (mensagens, arquivos externos);
- o que fazer se a etapa escolhida vier depois de uma aprovação;
- rota candidata: `POST /api/workflows/runs/:id/rerun` com `{ fromStep }`.

### 9.3 Conforto de edição e minimapa (decisão futura)

A passada de QA do canvas entra na F3.2; features novas de edição, não:

- snap/alinhamento na grade e guias;
- multi-seleção e mover vários elementos juntos;
- duplicar nota/container;
- atalhos extras de teclado;
- minimapa de navegação (hoje a spec o trata como fora de escopo; a decisão de
  incluí-lo fica para uma rodada futura).

### 9.4 Expressão livre no IF/Else (pode ou não entrar)

Decidido usar o grupo E/OU agora. A expressão livre fica como opção futura,
**sem compromisso de entrar**. Se entrar, será uma gramática fechada, nunca
`eval`/`new Function`: campos pontuados, literais, `and`/`or`/`not`,
parênteses e os comparadores atuais; limite de tamanho e profundidade; erro de
parse falha a etapa com mensagem clara. Não há decisão sobre aritmética ou
funções (`length`, `*`); isso só se a necessidade aparecer.

### 9.5 Ferramentas por etapa (adiada)

O dono decidiu deixar a fatia 2 para depois (09/11/2026). O desenho está na

### 9.6 Seleção de skills por etapa: snapshot x curinga

Futuro: permitir que o usuário escolha entre “all skills” (curinga, passa a

entrega, o padrão é o snapshot: ligar um grupo grava os nomes existentes naquele
momento, e uma skill nova não entra sozinha.

## 10. Critérios de aceite

1. Uma etapa manual para a run em `waiting_manual` sem abrir thread nem turno.
2. Continuar retoma exatamente aquela etapa, uma única vez.
3. Reiniciar o app mantém a run parada.
4. Apagar Workflow/run com run manual ativa responde 409.
5. Uma etapa de script `.py` e uma `.ts` gravam `result.json` e são verificadas.
6. Nenhuma etapa ganha ferramenta que o bot não tem. *(adiado junto com a
   fatia 2)*
7. Um grupo `all` só passa com todas verdadeiras; `any`, com pelo menos uma;
   uma condição antiga de uma linha continua carregando e rodando.
8. Uma rotina não pode ser salva apontando para Workflow cuja primeira etapa é
   manual; as demais etapas manuais não bloqueiam a rotina.
9. Nota e container passam pelo roteiro da seção 6 sem perda de layout ao
   salvar e reabrir.
10. Etapa sem seleção de skills roda com zero skills das três origens.
11. No grupo bot só é possível escolher skills que aquele bot tem; bundled e
   imported são opt-in, desligados por padrão, e aceitam todas ou algumas.
12. Nome inválido ou fora do escopo é recusado no save; skill que sumiu depois
   do save falha a etapa com `skill "x" is not available for this Workflow step`.
13. A seleção faz parte da versão; abrir/salvar sem mudar não cria versão, e
   `script`/`condition` não ganham o campo.
14. Turnos fora de Workflow não mudam; o painel da F2 mostra a seleção da etapa.
